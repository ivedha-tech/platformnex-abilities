# Refinement and Evaluation Criteria

Use this rubric in phase 2. Apply the dimensions that matter for the idea at hand.

## 1. User value

The most important dimension; if value is unclear nothing else matters.

**Painkiller or vitamin.** A painkiller solves an acute, frequent problem; people describe it with emotion, have built workarounds, and will switch. A vitamin is pleasant; people nod and keep their habits.

Ask:
- Can you name three specific people with this problem today?
- What do they do instead? The real competitor is the current workaround.
- What would make them switch?
- How often does the problem occur? Daily beats monthly.
- Is it pull (people ask for it) or push (you think they should want it)?

Warning signs: "everyone could use this"; "like X but better"; real but rare problems.

## 2. Feasibility

**Technical:** does the core technology work reliably; what is the hardest part and is it known or novel; which third parties or data sources are outside your control; how large is the minimum stack.

**Resource:** the smallest team and effort for an MVP; missing expertise; legal, regulatory, or compliance needs.

**Time to value:** how soon something reaches users; whether a days-or-weeks version exists; what the critical path is.

Warning signs: "we first need to solve a hard research problem"; several dependencies that must all work at once; an "MVP" that still takes months.

## 3. Differentiation

Different, not merely better.

- How would a user describe it to a friend, and is that compelling?
- What does it do that nothing else does?
- Can a competitor copy it in a week?
- Do users care about the difference, or only builders?

Types of differentiation, strongest first: new capability; 10x improvement; new audience; new context; better UX; cheaper (easily competed away).

Warning signs: differentiation lives only in technology; "faster/cheaper/prettier" with no structural reason; the differentiator is not what users value most.

## Assumption audit

For each direction, list assumptions in three tiers.

- **Must be true:** if wrong, the idea dies (for example, users will share their data). Validate before building.
- **Should be true:** if wrong, the approach changes but the idea survives.
- **Might be true:** secondary features and optimisations. Defer.

## Choosing between directions

|            | Easy to build | Hard to build |
|------------|---------------|---------------|
| **High value** | Do first | Worth the risk |
| **Low value**  | Only if trivial | Do not do |

Break ties with differentiation.

## MVP scoping

1. One job, done well.
2. Test the riskiest assumption first.
3. Scope by time box ("what can we build and test in N weeks?"), not by feature wish list.
4. Keep a mandatory Not Doing list.
5. If the first version does not feel a little embarrassing, you built too much.
